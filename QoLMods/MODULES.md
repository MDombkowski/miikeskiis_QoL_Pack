# How a mod becomes a module of miikeskii's QoL Pack

**Every Valheim mod of miikeskii's is written once, as a module, and released two ways:** inside the bundle, *miikeskii's QoL Pack* (one plugin, one section of its settings per mod), and on its own, as its single release. Set up by session 6-B on 2026-09-25 (card A10). The design and why it was chosen: card A10 and the research it links, in the vault.

This page is the convention. Follow it from a mod's first line; it is what keeps "one bundle" and "each mod on its own" both possible without reworking anything.

## The shape

```
Games\Valheim\
├─ QoLMods\                the bundle, and only the bundle
│  ├─ QoLMods.csproj       compiles its own src\, kit\ and parts\, plus every module's src\ (one Compile line each)
│  ├─ src\Plugin.cs        the bundle's plugin: lists the modules, runs each one with the kit
│  ├─ kit\                 THE KIT, the one copy to edit: runs a module (QoLModule, ModuleHost, ModuleSettings …)
│  ├─ parts\<Part>\        THE PARTS, the one copy to edit of each: code several modules share (see "Parts")
│  ├─ tools\               package.ps1 (both zips) · sync-kit.ps1 · make-icon.ps1
│  └─ MODULES.md · README.md · CHANGELOG.md · icon.png
└─ <Mod>\                  one folder per mod, self-contained, so it can be published on its own with its history
   ├─ <Mod>.csproj         builds the single release from everything in the folder
   ├─ src\                 the module: all the mod's own code (the bundle compiles this folder from here)
   │  └─ Module.cs         its entry: class Module : QoLModule
   ├─ standalone\Plugin.cs its single release's plugin (never compiled into the bundle)
   ├─ kit\                 a copy of the kit, kept identical by QoLMods\tools\sync-kit.ps1; never edited here
   ├─ parts\<Part>\        only if it uses a part: a copy, kept identical the same way; never edited here
   ├─ tools\package.ps1    its own zip
   └─ README.md · CHANGELOG.md · CREDITS.md · (icon.png only once it is released alone)
```

XPortalMapPicker is the worked example of every rule below.

## What a module must do

1. **Live in its own namespace**, named exactly as its folder (`XPortalMapPicker`), with every one of its classes in it or below it. The bundle holds every module in one DLL, and the kit finds a module's patches by its namespace.
2. **Have one entry class, `src\Module.cs`: `internal sealed class Module : QoLModule`,** with three constants its single release's plugin attribute uses, `Guid`, `Name` and `Version`, and the overrides the kit asks for (`Id`, `DisplayName`, `ModuleVersion`, `SingleGuid`, `EnabledDescription`, `BindSettings`, `Resolve`). Optional overrides: `Update`, `LateUpdate`, `UndoSteps`, `KeepPatchesAfterError`, `SwitchedOffNote`, `ReadyMessage`, `DescribeMissing`, `UpdateTask`, `LateUpdateTask`, `OneSectionInBundle`, `SingleStandsAsideFrom`, `EnabledByDefault`. Each is explained in `kit\QoLModule.cs`. **Its `Name` becomes a section name in the bundle**, so it avoids the characters BepInEx refuses there (`= ' " [ ] \` and tabs); a module named "Tim's Tweaks" would run alone and fail in the bundle.
3. **Never reach for its host directly.** No `BaseUnityPlugin`, no `ConfigFile`, no `new Harmony(…)`, no `PatchAll`, no BepInEx `Logger`. Log with `Module.Log`, and run any work that could fail inside `Module.Guard("doing what", () => …)`. Module.cs gives both as static members that forward to its host (copy them from XPortalMapPicker).
4. **Bind settings only through `ModuleSettings`,** in `BindSettings`: `settings.Bind(part, key, default, displayName, order, description[, range[, customDrawer]])`.
   - A **part** is `ModuleSettings.General` or a name of the module's own, such as `"Map"`. In its single release each part is a section of its own file; in the bundle, all parts share one section named after the module (a large module can override `OneSectionInBundle` to get `"<Name> - <part>"` sections instead). **So a part's name is a section's name and avoids the same characters as the module's `Name` (rule 2):** Quick Fix's part "Grinding Wheel and Smith's Anvil" made BepInEx throw at binding and the module never started (65-B's review, card B22); the part is "Wheel and Anvil", and a fold's title row shows the apostrophe (its display name is free).
   - **Keys never change** once a version has been released. The bundle takes a single release's settings over by part and key. Part names too, where each part is a section of its own.
   - **Orders are unique across the whole module and below 1000** (the kit refuses 1000 and above). A higher order is listed first. A module whose parts are all sections of their own (`OneSectionInBundle` false) needs them unique only within each part, unless it lists its parts under one heading in the window (below), as Map View Rules does: eleven orders per section of rules (ten in 0.1.0), from 60 down (`src\Folds.cs`).
   - **A setting drawn the module's own way** in a configuration manager's window (F1) passes a `customDrawer`, an `Action<ConfigEntryBase>` that draws its value with Unity's `GUILayout` (kit since 2026-09-27, `ConfigurationManagerAttributes.CustomDrawer`; the project then references `UnityEngine.IMGUIModule`). Map View Rules' zoom settings are the worked example (`src\ZoomDrawer.cs`): a slider, its number and a "Use map zoom" button. Without a configuration manager the setting stays a plain value in the file.
   - **A setting that holds a list of the game's things** (pieces, items, creatures: prefab names, item:amount) gets a Pick button that picks them from pictures (since 2026-10-11, card B03): `Lists.Attach(entry, spec)` right after binding it, with the spec written from the module's own reading of the list (the list picker, in "Parts" below).
   - **Many parts under one heading, as fold-outs** (kit since 2026-09-28): a module with many sections of its own can list them all under its own heading in the window, each behind a title row that opens and closes it; the settings file keeps its sections. After binding, `ModuleSettings.HintsOf(entry)` gives a setting's hints to change: `Category` (the heading; `settings.SectionOf(ModuleSettings.General)` names the module's own), `Browsable` (listed or not: shudnal's ConfigurationManager reads it again while its window is open, BepInEx's own only as it opens; once set, set it to true, never back to null, to list it again), and `HideSettingName` and `HideDefaultButton` (a custom drawer gets the whole row). Map View Rules is the worked example (`src\Folds.cs`, `src\FoldDrawer.cs`, his pick of 2026-09-28): each section's title row is a setting of its own (`Unfolded`), and sections fold only with shudnal's 1.1.22 or later, decided at the module's first frame; with any other manager every section shows open under its title. shudnal's re-reads a hidden setting's `Browsable` only in its round of 64 settings a frame, so after a click the module asks it to rebuild its list at the next frame, from its `Update`, outside the window's drawing (Jötunn's `ConfigManagerUtils.BuildSettingList`). It also colours a drawn row by that row's own value, so the title row sets the "changed" colour by the section's rules, not by whether it is open. Plain characters in the window ("[+]"): its font may lack arrows.
   - **A section can be bound while the game runs,** through the same `ModuleSettings`, kept from `BindSettings` (Map View Rules' override sections, `src\Sections.cs`); a configuration manager shows it the next time its window opens. It can't be unbound: a section no longer wanted stays until the next start. The bundle's once-only takeover of a single release's settings doesn't reach it.
   - **A default changed after a release** (kit since 2026-10-06, card A63): BepInEx writes every default into the file at the first start, so a new default never reaches an existing file by itself. Right after binding an entry whose default changed, `BindSettings` calls `settings.MovedDefault(entry, oldDefault, step)` (`step` 1 for the module's first release that moved any, 2 for its next, and so on). The host then, after binding and the single-release takeover, moves each such entry to its new default where the file still holds the old one (compared as the file writes them), once per file: the hidden setting `DefaultsMoved` in General remembers the last step, and comes over with a single release's settings. It logs what moved. A section bound while the game runs is moved at once, by the step the file had at the start (Map View Rules' override sections). A module whose Enabled switch is off in a new file overrides `QoLModule.EnabledByDefault` and moves the switch too (`settings.MovedDefault(settings.Enabled, true, 1)`: Item Stand Icons). Its tests: session 38-B's scratch harness (the real `ModuleHost` and `ModuleSettings` on real settings files; 133 checks, 13 planted bugs caught).
   - **A setting several modules must agree on** (kit since 2026-10-08, card A69): `settings.BindShared(section, key, default, displayName, order, description[, range])` binds it in a section of its own, named the same in the bundle and in every single release, so in the bundle every module that binds it gets the one entry (BepInEx hands back the entry already bound under that section and key, with the first binder's description) and a player sets it once. A part keeps such settings' section, keys and texts in one place and each module that uses the part calls it from `BindSettings` (the chest service's `ChestSettings.Bind`). A module that may differ keeps its own value, with 0 meaning "follow the shared one" (the four chest mods' own "Chest range"). The once-only takeover of a single release's settings fills a shared section only into a file that had none at the start, so one module's old file never overwrites what a player set for them all.
   - **The Enabled switch is bound by the kit**, first in General, with the module's `EnabledDescription`. Read it through the entry the kit hands over (`settings.Enabled`).
   - Every setting takes effect at once: read its value when it's needed, never cache it at start (his rule 3: a setting for every preference).
   - **Defaults that change nothing a player already sees.** The pack reaches his friends at their next update, and every module in it is switched on. So a module that changes something already on screen (the map, a menu) changes nothing until a setting asks for it: Trader Circles' traders were all off at first (until card A63, below), and Map View Rules' All pins never hides or shrinks. His own taste goes into his own settings. A module that adds something new behind a key of its own (Add to Cart's window) needn't wait. His own call can override the rule: Reserve Stock's padlock button in every chest window is on by default at his word after his test (2026-09-28); and Portion Control, which replaces BetterSplitDialog, is on for everyone out of the box at his call before it was built (2026-09-30): its split window stands aside while BetterSplitDialog is installed, so a friend who keeps it sees no change there; its chest window's -1 and Max weight (0.2.0, his feedback) are new buttons that change nothing the game shows, on for everyone at his word. Terraformer's own terrain tools are in the hoe's and cultivator's menus out of the box at his call (decision 4, 2026-09-30, before his test): it stands aside while AdvancedTerrainModifiers is installed, so a friend who keeps that sees no change either. Its preview grid (0.2.0), which takes the place of every terrain tool's round marker, the game's own included, is on for everyone at his call (2026-09-30). Comfort Build's Comfort tab in the build menu is on for everyone at his word before its build (2026-09-30): it adds a tab and changes nothing in the game's own four; its numbers on the game's own tabs stay behind a setting, off. Bar None's sky part (crops and saplings seeing the sky through listed pieces) is on for everyone out of the box at his call before its build (2026-09-29): a crop that can't grow is destroyed when it ripens by whichever game owns it then, so every friend on the pack must agree; its item part starts off (its reach, smoke and projectile parts did too until card A63). **His call of 2026-10-06 (card A63) made his own settings the pack's defaults**, over this rule, so a friend's first install works as his does; a moved default reaches a settings file written before it once, through `ModuleSettings.MovedDefault` (next point), only where the file still holds the old default, and Item Stand Icons is the one module off out of the box (`QoLModule.EnabledByDefault`).
5. **Make Enabled work live, both ways.** The kit calls the module's `Update` every frame while the module is active, also while it is switched off, so the module can follow the switch. Off takes back at once everything the module shows or changes; on puts it back without a restart. The kit applies a module's patches once, at start, and leaves them in place while it's off, so **every patch checks the switch first and changes nothing while it's off** (a prefix that could skip the game's own code returns true). The one exception is a patch that keeps the game from acting on the module's own messages, which must keep doing that while the module is off: Trader Circles' catch for the server's answers, which would otherwise become pins. Terraformer's patches that serve terrain strokes already on their way are the same kind (registering its tools after each rebuild of the game's list, reading a stroke's numbers, lending them for its one application, applying a square): a stroke placed a moment before the switch, or a friend's, must still apply as it was made. XPortalMapPicker reads its `Settings.Enabled`; the host's `IsOn` says "active and switched on", and Module.cs can forward it as a static like `Log`.
6. **Patch only with `[HarmonyPatch]` classes in its own namespace.** The kit applies them under the module's own Harmony ID (the single release's plugin ID when alone, `modprojects.qolmods.<id in lower case>` in the bundle), and removes them at the next frame if the module fails. A patch body that does real work runs inside `Module.Guard`, unless an error there should cost only that patch's own feature (then a guard of its own that catches it, turns that feature off and says so once: Bar None's sky part; Outfitter's Loadout Stands' hover lines, `Stands.HoverFailed`).
7. **Keep its errors to itself.** The first error inside `Module.Guard` (or `Update`/`LateUpdate`) switches that module off for the rest of the session. `UndoSteps` must then take back everything it shows or changed; each step runs even if the one before it fails. The kit then removes the module's patches at the next frame, unless the module sets `KeepPatchesAfterError` (Trader Circles does, for its catch); every patch of such a module must be safe to leave in place while it is off. Bar None keeps its patches after an error too, for a whole part: an error in its other parts must never let caged crops die at ripening, so its sky patches answer only to their switches and to their own guard (whose first error loses only that one test), and every other patch of it does nothing once the module is off. **One failed patch at start takes every class of the module off** (the kit patches them in one go), and in HarmonyX another mod's broken patch on the same game method makes every later patch of it fail; a module with a part that must survive gives each patch class a `Cleanup` that keeps the failure to that class (Bar None's `Broken.Patching`: it returns null, so HarmonyX swallows the failure, and takes the class's record back off the method). Outfitter does the same for Loadout Stands' patch classes (since 0.2.0, job 30: `src\Stands\StandPatches.cs`, `Stands.Patching`): a stand patch that can't be applied switches only the stands off for the session (the hover text's only their hover lines), never Outfitter's window or equip.
8. **Find other mods at start, never require them in the bundle.** In `Resolve`, look them up in `Chainloader.PluginInfos` and add a plain name to `missing` for anything it can't work without; the kit then leaves only that module off, with the module's `SwitchedOffNote`. In the bundle, add a soft-dependency line for that mod on `QoLMods\src\Plugin.cs`, so it starts before the bundle. The single release may declare it as a hard dependency, as XPortalMapPicker does with XPortal.
9. **Stay client-side** (his rule 6): Jötunn's `NetworkCompatibility(NotEnforced)` is on both plugins, and one level covers the whole bundle. A mod that needs the server is discussed with him first, and ships separately.
10. **Name its Unity objects `<Id>_…`** (`XPortalMapPicker_MapButton`), so modules never find each other's objects.
11. **Keep its credits in `CREDITS.md`** in its own folder, in XPortalMapPicker's shape: code copied in, code or ideas adapted, what it works with at run time, assets, and the note on AI-written code (his rule 5). The bundle's package gathers them all. **Its project file declares that it's made with AI**, as Thunderstore asks of AI-made mods: copy XPortalMapPicker's `AssemblyMetadata` items (`AI_Assisted_Creation`, `AI_Model_Vendor`, `AI_Model`), and say so in its README before it's released on its own.
12. **One version, three places:** `Version` in `src\Module.cs`, `<Version>` in its project, and a `## <version>` entry in its CHANGELOG. Both package scripts refuse a mismatch.
13. **Its CHANGELOG and README say what changed for a player, never whether or how it was tested** (no "not yet tested", no "By session …, reviewed, checked by a harness"): that belongs in the card and the session's record. His rule of 2026-10-10 (card B07), after Thunderstore rejected the pack as an untested AI mod for exactly those lines. The bundle's `tools\package.ps1` refuses them in the bundle and every module (`tools\check-shipped-text.ps1`), and since 0.45.1 in the built `QoLMods.dll` too, whose strings (every setting's description, every message) ship as well: 0.45.0's carried "untested" in two of Topper-Upper's settings (card B10). The same check refuses a DLL that holds this computer's user folder (the build's debug path, from a build in a worktree under the user profile), so the pack is packed from a folder outside it, such as `F:\Mod Projects` itself.
14. **Show a message on screen only through the kit's `Say`** (`Say.Center`, `Say.TopLeft`, or `Say.To` with an amount and an icon; kit since 2026-10-11, card B14), never with `MessageHud.ShowMessage` or a player's or creature's `Message`. The game's message texts never wrap, so a line longer than the screen is wide runs off both sides of it: `Say` breaks every line too wide at spaces into lines that fit, measured by the game's own message text (StoreStash's fitter, card A82, made the whole pack's after Topper-Upper's linking message ran off his screen; his word: *"This should be caught without me having to catch it."*). Keep a message short anyway: a fitted message is still read in the four seconds the game shows it. The bundle's `tools\package.ps1` refuses a DLL whose code calls the game's message methods anywhere outside `QoLMods.Kit.Say` (`tools\check-messages.ps1`, which reads the compiled code with Mono.Cecil, lambdas included). A module whose project lacked them references `Unity.TextMeshPro`, `UnityEngine.UI`, `UnityEngine.UIModule` and `assembly_guiutils` (the game's `Localization`) for it, or its single release won't build.

## Its single release

`standalone\Plugin.cs` is the whole of it; copy XPortalMapPicker's and change the names and dependencies:

```csharp
[BepInPlugin(Module.Guid, Module.Name, Module.Version)]
[BepInDependency(Jotunn.Main.ModGuid)]
[BepInDependency(Bundle.Guid, BepInDependency.DependencyFlags.SoftDependency)]   // so the bundle starts first, if it's there
[NetworkCompatibility(CompatibilityLevel.NotEnforced, VersionStrictness.None)]
public sealed class Plugin : BaseUnityPlugin
{
    private ModuleHost host;
    private void Awake() => host = ModuleHost.RunAlone(this, new Module(), Logger);
    private void Update() => host?.Update();
    private void LateUpdate() => host?.LateUpdate();
}
```

- **Its plugin ID is `modprojects.<id in lower case>`, and permanent:** it names the settings file, which the bundle reads once to take the settings over.
- **When the bundle is installed and runs the module,** `RunAlone` stands aside: it logs why and returns null, so the game is never patched twice. It asks the bundle through the bundle plugin's public `ModuleVersion(id)`, which answers only for a module the bundle started.
- **A single release from before the mod was a module doesn't know how to stand aside.** Such a module sets `SingleStandsAsideFrom` to its first single release that does (XPortalMapPicker: 0.4.0). At the first frame, when every plugin has started, the bundle checks: with an older copy running, the bundle's copy of that module steps back instead, and its log line says to update or remove the old copy. A mod that was a module from its first release leaves it null.
- **No icon of its own until it is released alone** (his rule, 2026-09-25). The icon is only the package's picture in the mod manager, never seen in game, and while a mod ships inside the bundle only the bundle's icon is seen. So a new module has no `icon.png` and no `make-icon.ps1`; its `tools\package.ps1` uses its own `icon.png` if there is one, else the bundle's `..\QoLMods\icon.png` (copy Map Zoom's). XPortal Map Picker keeps the icon it had from its own releases before the bundle.
- **Its package** is `drumcowski-<Folder>-<version>.zip`. Author and name never change once a friend has imported it (LESSONS_LEARNED, in the vault). The bundle's is `miikeskii-miikeskiis_QoL_Pack-<version>.zip` since 0.6.4, renamed at his word (card A30) so that his name is in the title Thunderstore shows (`miikeskii-QoL_Pack` for 0.6.3, whose Thunderstore listing was rejected; `drumcowski-QoL_Mods` before). The single releases follow when they are published.

## Adding a module to the bundle

1. **Create the mod's folder in its final place,** `Games\Valheim\<Mod>\`, before its first commit: it is never moved or renamed after (PROJECT.md). Start from Map Zoom's project file, `src\Module.cs`, `standalone\Plugin.cs`, `tools\package.ps1`, README, CHANGELOG and CREDITS.md: Map Zoom (`..\MapZoom\`, 2026-09-25) was a module from its first line, so it is the plainest starting point; XPortalMapPicker shows the extras a mod released before the bundle needs.
2. **`QoLMods\QoLMods.csproj`:** add one Compile line for its `src\`, and any reference it needs that the bundle lacks (to its own project too).
3. **Run `QoLMods\tools\sync-kit.ps1`.** It copies the kit into the new folder's `kit\`, reading the module folders from those Compile lines, and each part the mod uses into its `parts\<Part>\` (create that folder first; see "Parts").
4. **`QoLMods\src\Plugin.cs`:** add `new <Mod>.Module(),` to `Modules()` (the list's order is the order of the sections), and a soft-dependency line for every other author's mod it works with.
5. **The bundle's release:** raise its version (project file, `src\Plugin.cs`, CHANGELOG, whose entry names the modules' versions), and add the mod to its README, which is the pack's Thunderstore page: a one-line entry under its group in *What's inside*, a short section in *The mods* (a sentence or two, then a few bullets of what a player does and sees), its keys in *Default keys*, and any mod it replaces, needs or overlaps in *Other mods* (or *Playing with friends*, for anything that depends on friends having the pack). Plain words addressed to the player; no setting lists, versions, history or internal names (the configuration manager describes every setting, and the changelog holds the rest). Why the page is written that way: card A65, from a study of the most-downloaded Valheim mods' pages.
6. **Build both:** `QoLMods\tools\package.ps1` checks the kit copies and the versions, and writes the bundle's zip and every single release's zip.
7. **`Games\Valheim\README.md`:** a row for the mod.

## Parts: code several modules share

**A module never uses another module's code** (each single release must build and run alone). Code that several modules need, such as the chest service, is a **part** instead: shared source, compiled into each plugin that needs it, the way the kit is. Decided by session 9-B on 2026-09-25 (card A11), for the chest service that Add to Cart, our own craft-from-chests (A27) and Reserve Stock (A12) all use.

```
QoLMods\parts\<Part>\      the one copy to edit; the bundle compiles it once, whichever modules use it
<Mod>\parts\<Part>\        a copy in each mod that uses it, kept identical by tools\sync-kit.ps1; never edited there
```

1. **A mod uses a part by having its folder:** create `<Mod>\parts\<Part>\` and run `QoLMods\tools\sync-kit.ps1`, which fills it. The mod's own project compiles it (everything in the folder is compiled); the bundle compiles only its own `parts\`, never a module's copy. `sync-kit.ps1 -Check` (run by the package script) fails if a copy differs, or if a mod's `parts\` names a part that doesn't exist.
2. **A part lives in `namespace QoLMods.<Part>`** (the chest service: `QoLMods.Chests`), with every class `internal`, like the kit. Each plugin holds its own copy of each type, so two plugins carrying the same part never share state or clash.
3. **A part has no switch of its own, and settings only where every module must agree** (since 2026-10-08, card A69: four copies of the far-chest switch had one left off). Each module that uses it passes what its own settings say, each time it asks (the chest service: a `ChestRules`), and hands itself over as a user (`ChestUser`: its name, log and `Guard`), so the part's work for a module runs under that module's rules: an error while serving it switches off only that module (rule 7). A choice that must be the same for every module is one shared setting the part names and each module binds (`ModuleSettings.BindShared`; the chest service's `ChestSettings`: the range, "Chests beyond the server's reach", the log lines; and its `PerformanceMods`, in a section of its own: what the pack changes in other mods made for speed).
4. **A part's patches are its own, applied once per plugin, at the game's start, and never removed by a host.** A part patches with an explicit `Harmony.Patch` under its own Harmony ID, `modprojects.<plugin assembly>.<part>` (the chest service in the bundle: `modprojects.qolmods.chests`; in Add to Cart's single release: `modprojects.addtocart.chests`), from a `Resolve` that every using module calls in its own `Resolve`; the first call patches, and each call adds to `missing` what the part can't work without. It never uses `[HarmonyPatch]` classes, so no module's host picks them up. Its patches must do nothing unless the part itself is waiting for something, and must be safe to keep for the whole session: a host removes only its own module's patches after an error, and the part's patch may still be needed by another module, or by an answer still on its way.
5. **A part that needs a turn every frame** gets it from each using module's `Update` (the chest service: `ChestClaims.Tick()`), and does its work once a frame however many modules call it. The kit calls a module's `Update` also while it is switched off, so a part keeps turning while any user of it runs.
6. **Two plugins with the same part installed at once** (the bundle and an older single release that doesn't stand aside, or two single releases): each copy is separate, with its own patches, and each must act only on what it started. The chest service catches only answers to its own requests, by chest; if two copies ask the same chest in the same instant, the owner answers only the first (it no longer owns the chest when the second arrives), and the second copy's claim just times out.
7. **Changing a part** is like changing the kit: edit only `QoLMods\parts\<Part>\`, run `tools\sync-kit.ps1`, rebuild the bundle and every mod that uses it, and note it in the bundle's CHANGELOG and in each using mod's CHANGELOG. Keep its members working for every mod that uses it.

**The chest service** (`parts\Chests\`), the first part: finds the chests he may use (`ChestFinder`, from a list its patch on `Container.Awake` keeps), counts what they hold from this computer's copies in one pass (`ChestStock.Survey`), and takes from them safely (`ChestFetch.Start`), claiming each one from its owner through the game's own open request first, and holding it for a few seconds after (`ChestClaims`); since StoreStash 0.1.0 it also puts into chests and moves between them, and does the quick stack itself (below). Add to Cart and Craft from Chests use it, Reserve Stock claims a chest through it for its key, and StoreStash quick stacks through it. Topper-Upper (since bundle 0.38.0, card A77) takes fuel and inputs for lights and stations only from chests this computer already holds (`MayChange`, `ChestStock.Remove`, never a claim), puts products and loose items away by the quick stack's routing (`StackRouting.Tiers`, `StackPlanner`), and keeps its own measured put from an item on the ground (`TopperUpper\src\Chests\GroundPut.cs`) and batch put-away (`Stow.cs`): candidates for the part.
- **A chest a friend on the pack has open is shared** (since bundle 0.10.0, card A37; `ChestShare`, whose header says how). The game never hands an open chest to anyone else, so the service asks the game of the player who has it open instead. Games on the pack learn of each other by a hello (routed messages `modprojects.chests.hello`, `modprojects.chests.take`, and a reply name per plugin); nothing is written into the world. A chest is shareable (`ChestShare.CanShare`) while its record says open, its owner said hello, and the owner's character stands at it; `Survey` counts it like any other, and a claim can carry takes through owners beside its claims (`ChestClaims.Start` with `ShareTake`s): each asks only what fits in his inventory (`ChestShare.Room`, which picks as `ChestStock.Take` picks and places as the game's `AddItem` places), the owner's game takes it with `ChestStock.Take` (sparing the stack in its player's hand) and replies with the items in the game's own format, and they land in his inventory before the claim settles (`ClaimResult.Shared`). **So a module never uses anything up in place in a chest a friend has open: it gets what arrived in his inventory, and uses it from there** (Craft from Chests: crafting during the bar, a station after its own chests, building at a click only, never ahead). A reply not in within 4 s counts as no answer; a later one is still delivered, once (only from the game asked), with a word; what doesn't fit by then is dropped at his feet. The owner measures what each want gave from what arrived in its scratch inventory, so another mod's error mid-take never misreports it. The rare cases, written down: a player whose game crashes or leaves between the owner's take and the reply's arrival loses what was in flight; the owner's game crashing right after its take, before the chest's record goes out (the reply goes at once, the record with the next send), leaves a copy. A friend's game without the pack (or an older one) never answers and is never asked: its open chests stay out of the counts, as before. **Sharing is on while any module using the service is on** (`ChestHooks.Resolve(missing, user)` registers each; `ChestShare.Sharing`): switched all off, his game refuses takes ("not sharing", which marks it so on the asker) and says so in a hello (protocol 0). With two plugins carrying the service at once (separate single releases, no bundle), the copy that registered the routed messages first shares, and only its own module's switch counts. A hold never drops a request for a chest open on this computer (`ChestClaims.Drop`), unless MultiUserChest is loaded: the game's own "in use" is the truth there, and nothing is marked. A take (`ChestStock.Take`) moves out of the chest only what is really still in it: if another mod moved the stack away, or part of it, while the copy arrived in his inventory, that much goes back out of his inventory, the copy itself first. With MultiUserChest loaded, a claim's "yes" whose chest never comes while its record says open counts as in use after 1.5 s (`ChestClaims.MultiUserChestWait`) instead of no answer after 5, and its prefixes on the open and stack requests are skipped whenever the hold dropped the request (`ChestHooks.AtFirstTurn`).

- **Chests' setups** (since StoreStash's chest setups, session 27-B, card A41, runbook job 24): a chest can be set up to take only some kinds of things, and the quick stack follows it. **The setup lives in the chest's own record**, one line of text under `ChestSetup.Key` ("modprojects.qolmods.setup"), beside Reserve Stock's mark: the unmodded server keeps it, friends on the pack follow it, a game without the pack sees an ordinary chest. `ChestSetup.Read(chest)` gives the text ("" for none); `ChestSetup.Write(chest, text)` writes it only as the chest's owner and sends the record at once (the same text again sends nothing), refuses a text longer than `ChestSetup.MaxLength` (4000, the catalogue's `ItemPicks.MaxLength`), and clears it with "" (never a removal, which would reach no other player). **The text is the catalogue's** (`ItemPicks`, below); the chest service only keeps it, and never needs the catalogue. **The quick stack follows setups only when its caller passes them:** `StackRules.Setups`, a `SetupRules` holding the caller's reading of a chest (`Of`: null for a chest without a setup, else how strongly it takes an item, 0 for not at all; StoreStash's is `Setups.Reading`, from `ItemPicks.Fit`) and the choices its settings make (null: setups ignored, as before them). **In `StackRouting`:** a set-up chest takes what its setup takes even when it holds none yet, and is then "meant for" the item as a chest holding it is (rank 0, so the "in use" count counts it); anything else it refuses, even what it holds (strict), unless `KeepHeld`. - **Where each thing sits,** as data (`Taxonomy`: a rule change is one line): each item's Take family and member, Gear's sub-headings, its equipment slot, food's preparation, its Craft kind and the quick picks it belongs to (`Items.Home`; `ItemHome.Groups`, from `Taxonomy.QuickPicks`, card A81: natural groups of one family such as Metal Ingots, Prepared Dishes or Stamina Foods, each one line of family, member, label, what it is and its rule; food's main stat is the game's own colour rule, `Items.FoodStat`); a piece's build categories, its most specific one and what it is made of (`Pieces.Home`). Things are named by the game's prefab names, item types and skills, never by English text, so the rules hold in every language; another mod's things fall back by their game type.
- **Each item's biome of origin** (`Biomes`, worked out once per world from the game's own data; moved here from Add to Cart).
- **Reading the game** (`GameFacts`): the prefab that stands for every prefab sharing a `$` name, each item's facts and home (cached per world and shared, so read-only), a piece's facts, a station's label by its prefab. Every lookup prepares itself; call `Biomes.Build(log)` first if you want its log line (otherwise it runs silently).
- **The things a window lists** (`Listings.Piece`, `Listings.Item`): a piece, a recipe's or station's product, or an item, made into a `Listing` the one way every mod makes them (where it sits, its biome, its order, its name in the game's favorites, and what the filter box searches, as `Browse.SearchText`). A module gives each its own key.
- **The orders** (`Orders`): his orders by default; a module offers each as a one-line setting and passes the lines to `Orders.From` (names left out go last, unknown names are ignored). StoreStash's sorting (0.3.0, job 32) sorts by them outside any window: `StoreStash\src\Sorting\SortOrder.cs` places an item by its family (the order a setting line gives), its member, Gear's sub-heading, then its biome, from `Items.Home` and `Biomes`.
- **The browsing rules** (`Browse`): a module asks for the list on the left (`Tree`, then `Shown`: no empty rows), what a pick shows (`InPick`; a picked list is kept by name as well as number, `ListPick` and `Resolve`), the filter (`Matches`), the Group choices with Auto (`GroupOptions`), the Sort choices (`SortOptions`), and the headings in order (`Sections`, a stable sort).
- **His lists** (`GameLists`): favorites and lists on the game's own `FavoritePieceList`, pieces under their prefab name and items under `item:` and theirs; it keeps the three cautions of the build-menu research (check before adding, only valid list numbers, never the save's bytes). A module that uses it calls `GameLists.Resolve(missingOptional)` in its `Resolve`.
- **Its tests:** the scratch harness checks the port item by item against the mock-up's own data script and its page's script on every pick (runbook job 6's Issues and insights, 2026-09-27).
- **The comfort groups** (`Taxonomy.ComfortGroups`, since Comfort Build 0.1.0): each `Piece.ComfortGroup` by name, with its label ("Chairs", "Rugs and Carpets"; no group is "Other"), in the game's own order. `ComfortLabel` names a group, `ComfortKind` says what follows a piece's comfort ("Comfort 2 (Chairs)"; a piece with no group "(each kind counts once)"), and `DefaultComfortGroupLine` is the order as a setting shows it (Comfort Build's "Order of the groups", read with `Orders.Apply`). Add to Cart's hover and Comfort Build's comfort line both name a piece's comfort with `ComfortKind`.
- **A setup's picks** (`ItemPicks`, since StoreStash's chest setups, session 27-B, card A41): which items something takes, by this classification: picks (`ItemPick`: a family, a member of one, one of Gear's kinds, or one item by its shared name), excepts (the same kinds, taken out again) and biomes (the biome labels, and "Other"; none: every biome). Biomes narrow the families, members and kinds picked; with none of those picked, the biomes alone take everything from them; a single item picked by name comes from any biome, on top of the rest; where a pick and an except both name an item, the more specific decides, and an except wins a tie. `Fit(sharedName)` says how strongly it takes an item (0: not at all; `Fit(name, home, biome)` from the facts alone, for a harness). Written as one line (`Text()`: "picks1|+m:Hides and Fabrics/Hides and Pelts|-i:$item_needle|b:Plains"), always in one fixed order, so two identical setups are identical text (`Same`), and read back (`Parse`), keeping parts a newer version wrote (ignored when matching, except that an unknown pick, "+...", counts as a family picked so biomes never widen to everything: a later version must never add a part that changes what a setup takes without a new version word); a text past `MaxParts` or `MaxLength` is kept whole and takes nothing (`TooLong`: cut short it would lose its biomes and excepts, written last), though Clear and a paste may replace it; a text starting with another version word is kept whole, takes nothing and is never rewritten (`Readable` false). At most `MaxParts` parts and `MaxLength` characters. **Families, members and kinds are its words by their labels:** a label renamed in `Taxonomy` goes into `ItemPicks.Renamed` by its place ("f:Old", "m:Family/Old", "k:Family/Member/Old", "b:Old biome", old to new, the family and member named as renamed: a member and a kind may share a label), so setups written with the old one read with the new; StoreStash's harness pins every label, so a rename can't go unnoticed. `AddBiome` takes only the catalogue's biomes (`IsBiome`); a record's are kept as they are. `AddAll` (pasting to add) says whether all of it fitted. `Describe` says it in words, the biomes right after what they narrow ("Hides and Pelts · Plains, plus Wolf Fang, except Needle"; biomes alone, "Everything · Plains"). **Since card A81 (session 44-B):** a pick can also be one of a family's quick picks ("+g:Metals/Metal Ingots"; as specific as a kind when it lies inside one member, as a member when it spans several), and a family, member, kind or quick pick taken can have biomes of its own ("+n:Mistlands,Ashlands:m:Gear/Weapons": `AddOwnBiome`, `RemoveOwnBiome`, `OwnBiomesOf`, `SetOwnBiomes`), which narrow it in place of the setup's biomes; the setup's biomes narrow the rest, and take everything from them only when no family, member, kind or quick pick is taken at all. Both are "+" parts, so an older version skips them (taking less, never more) and counts them as families; a change it makes beside one is read as made: a group it took whole, or left out, beside its narrowed self reads whole, or left out (a left-out's overruled narrowed part is kept as that version keeps it while it is the setup's only group, so the biomes never widen). A quick pick left out ("-g:...") would make an older version take more, so a setup holding one is written with the version word "picks2" (`VersionWord`, `VersionWithGroupExcepts`), which an older version keeps whole and follows in nothing; every other setup keeps "picks1" (`IsVersion`, `LooksLikeSetup` for the clipboard). `TextWithoutBiomes` is the text with no biomes at all (Stack Overflow's "ignoring biomes"). Renamed labels: "g:Family/Old" too. Its tests: session 44-B's scratch harness, with the reader released before card A81 compiled beside today's. The chest service keeps it in a chest's record (`ChestSetup`, above).

## Changing the kit

Edit only `QoLMods\kit\`. Then run `tools\sync-kit.ps1`, rebuild the bundle and every single release, and note the change in the bundle's CHANGELOG. Keep the kit's members working for the modules that already use them: every module compiles against it. `tools\sync-kit.ps1 -Check` (run by the package script) fails if any mod's copy differs.

## Testing

The bundle is what he tests every time. A single release is tested in game when a friend wants one. Every test follows PROJECT.md's *How to run*: back up first, pack the zips, and he imports them.

## Building and packing the bundle

The bundle's README is its page on Thunderstore, so how to build it is here. The pack is GPL-3.0 (`LICENSE`, his pick, 2026-09-27), and its source is public at https://github.com/MDombkowski/miikeskiis_QoL_Pack (the README and the package's website point there). The package itself never carries the source: Thunderstore's moderators rejected 0.6.3 for it. `tools\package.ps1 -SourceTo <that repository's folder>` mirrors this folder and every module's into it, side by side, without `bin\`, `obj\` or `dist\`, with `LICENSE` and a README at its root. It refuses a source file that names this computer's user, user folder or git email, so keep machine paths out of the source (`$(APPDATA)` in a project file, `$env:APPDATA` in a script).

- **Build:** `dotnet build -c Release` in this folder. The result is `bin\Release\net472\QoLMods.dll`.
- **What's where:** this folder holds only the bundle: its plugin (`src\Plugin.cs`), the kit (`kit\`), which runs every mod as a module, and the parts several mods share (`parts\`: the chest service; the catalogue, which says where each thing sits and how every mod browses; and the pictures, the grey copies of the game's icons). Each mod's code stays in its own folder beside this one and is compiled from there, so the bundle and each mod's own release come from the same files. How a module and a part are written and added: the sections above.
- **Package:** `tools\package.ps1` checks that every mod's copy of the kit and of each part it uses matches this one (`tools\sync-kit.ps1 -Check`), that the project file, `src\Plugin.cs` and `CHANGELOG.md` agree on the version, that `README.md` and `CHANGELOG.md` are what Thunderstore takes (no byte-order mark, under 100,000 characters), builds the bundle, and writes `dist\miikeskii-miikeskiis_QoL_Pack-<version>.zip`. Its `CREDITS.md` gathers every mod's credits. It then builds each mod's own zip with that mod's `tools\package.ps1`; `-BundleOnly` skips that. The icon is drawn by `tools\make-icon.ps1`.
- **References:** it compiles against the game's DLLs and the BepInEx, HarmonyX and Jötunn DLLs where they are already installed. Nothing is downloaded and nothing is copied or written outside the mod folders. Override the two paths if yours are elsewhere: `-p:ValheimManaged="<Valheim>\valheim_Data\Managed" -p:ModProfile="<mod manager profile folder>"`.
